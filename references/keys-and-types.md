# Keys and Types

## Primary keys

| Table kind | Key | Why |
|---|---|---|
| Entity tables (users, orders, invoices…) — the default | `id uuid NOT NULL DEFAULT uuidv7()` | Native in PostgreSQL 18. Time-ordered, so inserts append to the B-tree like a sequence (no random-UUID index bloat); globally unique, so ids can be generated by consumers, merged across shards or exposed without leaking counts. |
| Small catalogs that rarely change (countries, currencies, statuses with metadata) | `id integer GENERATED ALWAYS AS IDENTITY` (or `smallint`) | Compact FKs on large tables, human-readable. `GENERATED ALWAYS AS IDENTITY` is the standard replacement for `serial` (same behavior, owned sequence, blocks accidental manual ids). |
| Catalogs with a stable natural code | the code itself (`currency_code char(3)`) | Only when the code is truly immutable (ISO codes). |

Any other choice (bigint identity for a hot table, a composite PK) needs an ADR. Partitioned tables need the partition key in the PK: `PRIMARY KEY (id, created_at)`.

uuidv7 embeds the creation time: don't expose ids where the creation timestamp is sensitive, or use `gen_random_uuid()` (v4) for that table and record it in an ADR.

Seeds for identity catalogs never hard-code the generated id; they conflict on the natural key (`ON CONFLICT (code)`), and FKs from other seeds look it up by code.

## Types

| Use | Type | Avoid |
|---|---|---|
| Instants | `timestamptz` | `timestamp` (no time zone → ambiguous) |
| Calendar dates | `date` | text dates |
| Money | `numeric(14,2)` (or `numeric(19,4)` for rates/FX) + currency code | `float`, `real`, `money` |
| Text | `text`, with a `CHECK (char_length(x) <= n)` when the limit is a business rule | `varchar(n)` as a habit, `char(n)` |
| Case-insensitive identifiers (email) | `citext` extension, or `text` + unique index on `lower(email)` | — |
| Booleans | `boolean NOT NULL DEFAULT false` | nullable booleans (three states) |
| Semi-structured attributes | `jsonb` (see normalization-and-adr.md) | `json`, text-encoded JSON |
| Ranges (bookings, validity) | `tstzrange`, `daterange` | two loose columns when overlaps matter |
| IP addresses | `inet` | text |
| Counters, quantities | `integer` / `bigint` with `CHECK (x >= 0)` | numeric for integers |

## Nullability and integrity

- **`NOT NULL` by default.** A column is nullable only when "unknown/absent" is a real state.
- **Every FK declares `ON DELETE`**: `RESTRICT` by default (you can't delete a customer with orders); `CASCADE` only for owned children (order → order_items); `SET NULL` for optional links.
- **`CHECK` constraints for domain rules**: positive amounts, valid ranges, `start < end`, allowed status values.
- **Unique constraints for natural keys**, tenant-scoped in multi-tenant tables: `UNIQUE (tenant_id, email)`.

## Status and enumerations

- Few, stable values with no metadata → `text NOT NULL` + `CHECK (status IN ('draft', 'sent', 'paid'))`. Changing the list is one migration that replaces the check.
- Values with metadata (labels, ordering, flags) or that business users manage → a catalog table with an identity key and a FK.
- **Avoid native `ENUM` types**: values can't be removed or reordered easily, and `ADD VALUE` has transaction restrictions.

## Audit columns

Every **mutable** table:

```sql
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now()
```

`updated_at` is maintained by the shared trigger function `set_updated_at()` (`templates/database/functions/set-updated-at.sql`), attached in `database/triggers/updated-at.sql`:

```sql
CREATE OR REPLACE TRIGGER trg_users_updated_at
  BEFORE UPDATE ON public.users
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
```

**Immutable tables** (ledgers, audit logs, events) have `created_at` only, plus `prevent_mutation()` attached `BEFORE UPDATE OR DELETE`, and `UPDATE, DELETE` revoked from consumer roles.

Who-did-it columns (`created_by`, `updated_by`) only when the product needs them; full history belongs in an audit table, not in more columns.

## Soft delete (optional, asked at scaffolding)

```sql
deleted_at timestamptz NULL
```

When enabled:
- Uniqueness becomes partial: `CREATE UNIQUE INDEX uq_users_tenant_id_email ON users (tenant_id, email) WHERE deleted_at IS NULL;`
- Hot indexes become partial with `WHERE deleted_at IS NULL`.
- Consumers read through views or a policy that filters `deleted_at IS NULL`; decide which and write it in an ADR.
- Plan a purge (retention job) — soft-deleted rows still count for size and privacy obligations.

Apply soft delete only to tables where restoring or auditing deletions is a requirement; ledgers never delete.
